# 지도 없이 스스로 길을 찾는 자율주행 알고리즘

지도 없이, 라이다만으로 스스로 길을 찾는 RC카 시뮬레이터.
하드웨어와 ROS는 범위 밖이다. 알고리즘만 파이썬으로 구현했다.

지금 기본 계획기는 **하이브리드 A\***다. 여기까지 온 과정을 아래
"알고리즘 발전 과정"에 단계별로 적었다. 각 단계는
**알고리즘 → 문제점 → 해결책 → 향상된 알고리즘** 순서로 이어진다.

## 빠른 시작

```bash
pip install -r requirements.txt
python run.py                          # 창으로 보기 (하이브리드 A*)
python run.py --scenario trap          # 다른 시나리오
python run.py --planner tangent        # 예전 접선 그래프 계획기
python run.py --sensor tof_sweep_rear  # 싼 센서 조합으로 보기 (목록은 --list)
python run.py --bench                  # 전 시나리오 성능 측정
python run.py --list                   # 시나리오 목록
python -m tests.test_hybrid            # 하이브리드 A* 시험 (몇 초)
python -m tests.test_robot             # 실물 통신과 주행 시험 (몇 초)
python -m rccar.car_specs              # 우리 차를 잰 값, 빈칸, 펌웨어에 옮길 값 보기
python run.py --car ours               # 잰 우리 차 크기로 시뮬레이션
python run_error_split.py              # 오차 분해 (지도 30개, 몇 분)
python run_circle_model.py             # 처음 기하 모델(0단계)을 고정 배치에서 표로 보기
python run_circle_model.py --layout cup --show   # 한 배치를 그림으로
python run_circle_model.py --geogebra  # GeoGebra 로 작도해 맞춰 볼 숫자
python run_circle_model.py --search 1000         # 무작위 배치에서 실패 찾기
python -m tests.test_circle_model      # 처음 기하 모델 시험 (몇 초)
python run_robot.py --fake --seed 2005 # 부품 없이 실물 주행 프로그램 시험 (기록은 logs/ 에)
python -m tests                        # 시험 전체 (접선 그래프 시험 때문에 수십 분)
```

## 알고리즘 발전 과정

1~2단계는 `ALGORITHM.md`와 `HANDOFF.md`에 남은 기록이다.
3단계부터는 같은 조건에서 고치기 전과 후를 나란히 잰 값이다.
단계마다 측정 조건이 달라서, 서로 다른 단계의 숫자끼리는 비교하지 않는다.
0단계는 계획서에 적은 처음 모델을 나중에(2026-10-08) 코드로 옮겨 잰 것이다.

### 0단계. 처음 생각한 기하 모델 (계획서의 알고리즘 A)

**알고리즘**

계획서 6-가에 적은 모델을 교과서(공통수학2 도형의 방정식) 방식 그대로 옮겼다.
`rccar/circle_model.py`, `rccar/circle_avoider.py`, 실행은 `run_circle_model.py`.

- 장애물은 원, 차는 점. 기둥 반지름에 차 반폭을 더해 부풀린다.
- 목표까지 선분이 원을 지나는지는 **판별식**과 **수선의 발**로 본다. 판별식만 보면 차 뒤의 원도 걸린다.
- 접선은 **기울기 이차방정식** `(a² − r²)m² − 2abm + (b² − r²) = 0` 의 두 근으로 구한다.
  `a² = r²` 이면 한 접선이 수직이라 따로 처리한다. 접점은 중심에서 접선에 내린 수선의 발이다.
- 눈앞에서 목표를 막는 **가장 가까운 원 하나**만 보고, '접선 + 호 + 접선' 이 짧은 쪽으로 비켜 간다.
  길이가 같으면 오른쪽. 호의 길이는 원 둘레 × (중심각 / 360°).
- 원을 따라 돌다가 중심에서 '지금 위치-목표' 직선에 내린 수선의 발이 뒤로 넘어가면 떠난다.
- 반복이 끝나도록 **처음 부딪힌 곳보다 목표에 가까울 때만** 떠난다 (기준선 규칙).

조사해 보니 이 구조는 **Bug 알고리즘** 계열(Lumelsky, Stepanov, 1987)이고,
기준선 규칙은 그중 Bug2 의 종료 조건과 같은 생각이다. TangentBug(1998)가 그 후속이다.

**계획서에 없던 빈 곳**

원에서 떠나는 순간 차는 원 위에 서 있다. 다음 원을 비켜 가는 접선이 방금 떠난 원을 다시
지나면 그 원을 피해야 하는데, 원 위의 점에서는 그 원에 접선 두 개를 그을 수 없다.
계획서 규칙으로는 할 일이 정해지지 않는다. 무작위 배치 1000개 중 94개가 여기서 멈췄다.
**떠나려던 원이 다시 길을 막으면 떠나지 않고 계속 따라 돈다**는 규칙을 더해 메웠다.

**결과** (1.5 m 평면, 지름 60~100 mm 기둥 3~6개, 차 반폭 7 cm 가정)

| 배치 | 결과 | 경로 / 직선 |
|---|---|---|
| 기둥 하나 (`one`) | 도착 | 1.006 |
| 중심이 직선 위 (`tie`) | 도착, 오른쪽 규칙 | 1.011 |
| 흩어진 기둥 다섯 (`scattered`) | 도착 | 1.027 |
| 붙은 기둥 둘 (`close_pair`) | **충돌** | - |
| 벽처럼 늘어선 기둥 (`wall`) | **충돌**, 좌우를 57번 바꿈 | - |
| 컵 모양 (`cup`) | **충돌**, 좌우를 87번 바꿈 | - |
| 무작위 1000개 | 981 도착, 16 충돌, 3 멈춤 | 평균 1.009 |

- **부풀린 원끼리 안 겹치는 배치는 415개 전부 도착했다.** 실패 19개는 전부 원이 겹친 배치였다.
- 원이 겹치면 한 원의 접점이 옆 원 안에 묻힌다. 원 하나만 보는 규칙은 이걸 모르고 그 접점으로 간다.
  ALGORITHM.md 2.5 절(겹친 장애물 병합)이 1단계에서 따로 필요했던 이유가 여기서 드러난다.
- 손으로 계산한 '접선 + 호 + 접선' 길이와 실제로 걸어 본 길이가 소수 셋째 자리까지 같다 (`--geogebra`).
- 센서 거리를 0.15 m 까지 줄여도 도착률은 97.5% 로 크게 안 변했다. 기둥이 듬성하면 눈앞만 봐도 충분하다.
- 기울기 방식은 수직 근처에서 불안정할 것으로 예상했지만, 재 보니 접점 오차가 1e-10 이하였다.
  단점은 정확도가 아니라 수직 접선을 따로 다뤄야 하는 번거로움이다.
  1단계는 각도 방식(`acos(r/d)`)을 썼는데, ALGORITHM.md 3.2 절은 그 이유를 이차방정식을 풀지 않아
  원에 아주 가까운 점에서도 안정적이라서라고 적었다.

**이 모델이 가정하고 넘어간 것**

최소 회전 반경, 센서 잡음, 차의 실제 움직임이 없다. 차가 점이라 호를 그대로 따라간다.
이 가정이 얼마나 손해를 보는지는 실제 차와 비교해 재야 한다 (오차 분해, 예정).

### 1단계. 접선 그래프 + A\*

**알고리즘**

장애물을 안전 여유만큼 부풀리면 차를 크기 없는 점으로 볼 수 있다.
장애물을 피하는 최단 경로는 고무줄처럼 **접선 → 원호 → 접선** 모양이 된다.
출발점, 목적지, 모든 접점을 역으로 놓고 지하철 노선도를 그린 뒤 A\*로 최단 경로를 찾는다.
갈림길을 하나씩 따라가면 장애물 n개에 경로가 2의 n제곱 개로 늘어나서 이 방식을 택했다.

**문제점**

노선이 5,709개인데 전부 미리 충돌 검사를 했다. **계획 한 번에 2,253 ms**가 걸렸다.
계획은 1초에 열 번 해야 한다.

**해결책: 지연 충돌 검사**

노선도를 만들 때는 회전 방향이 맞는지만 본다. 충돌 검사는 A\*가 그 노선을
실제로 꺼낼 때 한다. 길이를 하한 비용으로 먼저 넣고, 꺼낼 때 실제 비용으로 고친다.

**향상된 알고리즘**

평균 25개 노선만 검사하게 되어 **24 ms**가 됐다. 약 90배 빠르다.
경로 비용은 전수 검사와 소수점까지 같았다. 근사가 아니다.

### 2단계. 지연 평가 접선 그래프

**문제점**

실제로 주행시키자 계산이 아니라 상황에서 문제가 터졌다.

- **오목한 물체.** ㄷ자 벽에 볼록껍질을 씌우니 입구가 메워져, 안에 있던 차가
  "장애물 내부"로 판정됐다.
- **제자리 진동.** 부풀린 영역에 들어가는 것을 위반으로 보니, 탈출과 주행이
  무한히 번갈아 일어났다.
- **영구 정지.** 비상 정지가 속도만 0으로 만들어서, 코를 박은 차가 그대로 멈췄다.
- **못 따라가는 곡선.** 부풀림 반지름을 최소 회전 반경과 같게 두니, 핸들을 끝까지
  꺾어야 겨우 도는 호가 나와 추종 오차가 그대로 침범이 됐다.
- **막다른 골목.** 목적지 쪽 최단 경로만 보니, ㄷ자 골목에서 먼저 뒤로 빠져나와야
  한다는 판단을 못 했다.

**해결책**

- 센서 점렬을 볼록한 조각으로 쪼갠다. 조각들이 끝점을 공유해서 모서리를 도는 경로가 저절로 생긴다.
- 계획용 반경과 안전용 반경을 나눈다. 탈출을 시작하면 최소 시간은 유지한다.
- 코가 막힌 채 멈춰 있으면 후진 탈출로 넘긴다.
- 부풀림 반지름의 하한을 최소 회전 반경의 1.6배로 둔다.
- 일정 시간 목적지에 가까워지지 않으면 격자 A\*로 탈출로를 찾는다.

**향상된 알고리즘**

접선 그래프에 예외 처리와 격자 대체 경로를 더했다.
당시 기록으로 다섯 시나리오 모두 도착했고, 뒷바퀴 축 기준 충돌은 없었다.

### 3단계. 예외 처리가 붙은 접선 그래프

**문제점**

경로를 너무 자주 갈아탔다. 새 경로가 10% 이상 좋을 때만 바꾸는 고집 장치가
있었는데 사실상 작동하지 않았다.

원인은 **비교 기준 시점이 달랐던 것**이다. 기존 경로의 비용은 그 경로를 고르던
옛 위치에서 잰 값이고, 새 경로의 비용은 지금 위치에서 잰 값이었다.
차가 앞으로 갈수록 기존 값만 낡아서 커지니 새 경로가 늘 싸 보였다.

**해결책: 같은 시점으로 비교**

기존 경로 비용을 남은 길이의 비율만큼 깎아서 지금 시점의 값으로 맞춘다.

**향상된 알고리즘**

| | 고치기 전 | 고친 후 |
|---|---|---|
| pillars 경로 교체 | 36회 | 14회 |
| narrow 경로 교체 | 70회 | 10회 |
| narrow 도착 | 25초 안에 실패 | 13.1초 |

**시도했지만 버린 것.** 크게 꺾이는 교체에 더 높은 문턱을 두는 장치도 만들었다.
혼자서는 괜찮았지만 위 수정과 같이 쓰면 문턱이 이중으로 높아졌다.
`pillars`가 52.1초, 교체 129회, 계획 평균 4,983 ms로 망가져서 뺐다.

### 4단계. 고집 장치를 고친 접선 그래프

**문제점**

계획된 경로가 **차 뒤로 되돌아가라고** 지시하는 순간이 있었다. 그러면 추종기가 쫓는
점이 차 뒤에 놓여 핸들을 끝까지 꺾게 되고, 장애물에 가장 가까이 붙는다.

차의 진행 방향과 경로 출발 방향이 100도 넘게 벌어진 순간을 세었다.
3단계 수정을 마친 상태에서 `pillars` 7회, 최대 179도였다. `walls`에서는 30회였다.
3단계 수정은 이 문제를 거의 줄이지 못했다. 수정 전에도 각각 7회와 32회였다.

원인은 **계획기가 차의 방향을 모른다**는 것이다. 출발점을 점 하나로만 봐서,
뒤로 가는 길이 짧으면 제자리에서 돌 수 있다고 착각했다.

**해결책을 찾기까지 세 번 시도했다**

| 시도 | 내용 | 결과 |
|---|---|---|
| 회전 방향 잠금 | 한 번 정한 쪽의 반대편 접점을 아예 만들지 않는다 | `walls` 41.3초에서 50.4초로 **악화**. 반대편도 멀쩡한 우회로였다 |
| 뒤로 가는 첫 구간 금지 | 차 방향과 크게 어긋나는 첫 구간을 만들지 않는다 | 되돌아가기 0회, `walls` 18.0초. 그런데 **`trap` 실패**. 골목에선 돌아 나오는 게 유일한 답이다 |
| **뒤로 가는 첫 구간에 벌점** | 금지 대신 아주 비싸게 만든다 | 둘 다 해결 |

벌점 크기는 12, 30, 60, 120을 재 봤다. 30에서는 `walls`가 도착에 실패했고,
60에서는 `trap`이 47.3초로 느려졌다. 어중간한 벌점이 가장 나빴다. 120으로 정했다.

**향상된 알고리즘**

주행 시간은 3단계 수정까지 마친 상태와 비교한 값이다.

| 시나리오 | 되돌아가기 | 주행 시간 |
|---|---|---|
| pillars | 7회에서 0회 | 18.4초에서 18.9초 |
| walls | 30회에서 0회 | 41.3초에서 18.0초 |
| narrow | 0회 | 13.1초 그대로 |
| trap | 7회. 골목에서 돌아 나오는 데 필요한 만큼 | 25.1초에서 23.0초 |

`walls`는 되돌아가느라 버리던 시간이 사라져 절반 이하가 됐다.
`pillars`는 0.5초 느려졌다.

### 5단계. 뒤로 가기 벌점이 붙은 접선 그래프

**문제점**

남은 문제들은 고쳐서 없앨 수 있는 버그가 아니라 **방법 자체의 한계**였다.

- **좁은 틈을 못 지나간다.** 안전 여유는 0.52 m면 되는데, 곡선을 차가 따라갈 수
  있게 부풀림 반지름을 0.85 m로 키웠다. 두 장애물 표면 사이가 1.69 m보다 좁으면
  하나로 합쳐진다. 폭 0.28 m인 차가 1.5 m 문을 못 지나갔다.
  접선 그래프에서는 호가 곧 부풀린 경계라서 이 두 값을 나눌 수 없다.
- **같은 계산을 매번 반복한다.** 0.1초마다 노선도를 처음부터 만들고 처음부터 찾았다.
  `trap`에서 계획 시간의 94%가 길 찾기였고, 계획에 넣은 원의 73%가 이미 지나친 뒤쪽 장애물이었다.
- **차체 접촉을 못 잡는다.** 시뮬레이터의 충돌 판정은 뒷바퀴 축 한 점만 본다.
  차체 사각형 전체로 다시 재니 `forest`에서 **기둥에 5 cm 파고들었고**,
  `trap`에서는 3 cm까지 붙었다. 기록상 "충돌 0건"이었던 것이다.

뒤쪽 장애물을 계획에서 빼는 수정도 해 봤다. 빨라진다는 증거를 못 얻었고 `trap`이
시간 초과되어 되돌렸다.

**해결책: 하이브리드 A\*로 교체**

- **상태에 방향을 넣는다.** 위치와 방향을 함께 들고, 차가 실제로 그릴 수 있는
  곡선 조각만 이어 붙인다. 제자리 회전 같은 경로는 후보가 되지 않는다.
  후진도 조각의 하나라서 골목에서는 자연스럽게 되돌아 나온다.
- **충돌을 실제 차체로 판정한다.** 차체를 원 세 개로 덮고, 점유 격자에서 만든
  거리장으로 검사한다. 회전 반경은 곡선 조각에만 들어가서 통로 폭과 섞이지 않는다.
- **필요할 때만 다시 찾는다.** 경로가 막혔거나, 차가 벗어났거나, 1.5초가 지났을 때만
  계획한다. 시간이 지나 찾은 새 경로는 남은 비용보다 15% 이상 싸야 갈아탄다.
- **예측 정지를 둔다.** 지금 명령대로 제동 거리만큼 갔을 때 차체가 닿으면 멈추고 다시 찾는다.

**향상된 알고리즘**

인공 지도에서 통과 가능한 최소 틈이 **1.69 m에서 0.7 m**로 줄었다.

### 6단계. 하이브리드 A\* 첫 구현

**문제점**

- **골목을 못 빠져나왔다.** 목적지까지의 거리 추정이 벽을 뚫고 샜다. 골목 안에서
  추정 거리가 벽을 통과하는 직선 거리인 13.0 m로 나와, 탐색이 벽을 향해 헤매다
  확장 상한에 걸렸다. 여덟 방향으로 퍼뜨린 뒤 막힌 칸을 한 번만 막아서 생긴 버그였다.
- **벽 옆에서 괜히 느렸다.** 경로 옆 여유가 작으면 세게 감속하게 했더니, 벽을
  따라 나란히 달릴 때마다 느려졌다. `walls`가 24.7초로 예전 계획기보다 느렸다.

**해결책**

- 방향 하나를 퍼뜨릴 때마다 막힌 칸을 다시 막는다. 추정 거리가 26.2 m로 바로잡혔고,
  확장 386번 만에 골목을 빠져나가는 경로를 찾았다.
- 감속을 약하게 줄였다. 제한을 거의 꺼도 차체 여유는 줄지 않았다.
  부딪힘은 예측 정지가 차체 기준으로 막고 있기 때문이다.
  `walls`가 24.7초에서 19.1초가 됐고, 차체 여유는 0.21 m에서 0.44 m로 오히려 늘었다.

**향상된 알고리즘**

### 오차 분해 (계획서 6-라, 2026-10-19 예비 결과)

`run_error_split.py`. 같은 지도에서 한 번에 하나씩만 실제에 가깝게 바꿔 달리고,
앞 단계보다 바뀐 만큼을 그 원인의 몫으로 본다. 센서는 실제 차와 같이 앞 ToF 하나(서보 회전), 후진 없음.

| 단계 | 바꾼 것 |
|---|---|
| 0 다 아는 차 | 지도를 처음부터 다 앎, 위치 추정 완벽 |
| 1 알고리즘 | 보이는 것만 앎. 센서는 이상적 (1도 간격, 잡음 없음, 원뿔 없음) |
| 2 센서 | 실제 ToF 흉내 (서보 15도 왕복, 원뿔 27도, 잡음) |
| 3 위치 추정 | 엔코더 없이 명령 속도와 자이로로 위치를 짐작 |
| 4 실차 | 바닥에 남은 궤적 (예정) |

**처음 세운 지표가 틀린 결론을 냈다.** 계획서는 "기준 경로 대비 길이 비" 를 주 지표로 잡았다.
그런데 지도 12개 중 8개에서 다 아는 차가 오히려 더 길게 달렸다. 계획기가 줄이는 것은 길이가 아니라
장애물에 가까울수록 벌점이 붙는 비용이라서, 다 아는 차는 좁은 틈을 피해 넓게 돌아가고
보이는 것만 아는 차는 못 본 기둥을 빈 땅으로 여겨 바짝 붙어 간다. 길이만 보면 "모르는 게 낫다" 가 된다.
그래서 **길이, 차체 최소 여유, 도달 오차를 늘 함께 본다.** 0 단계도 "이론적 최적" 이 아니라 "다 아는 차의 주행" 이다.

무작위 지도 30개, **시뮬레이터 기본 차** (폭 28 cm, 우리 차를 재기 전이라 예비 값):

| 원인 | 길이 비 | 차체 최소 여유 | 도달 오차 | 위치 추정 오차 |
|---|---|---|---|---|
| 알고리즘 | -2.1% | **-6.4 cm** | 0 | 0 |
| 센서 | **+7.6%** | +7.0 cm | 0 | 0 |
| 위치 추정 | -2.8% | -0.3 cm | **+30.5 cm** | +41.6 cm |

- 알고리즘: 못 본 기둥에 붙어 짧게 가는 대신 여유를 잃는다.
- 센서: 빛이 원뿔로 퍼져 기둥이 실제보다 크게 찍힌다 (원뿔 끝 호 전체에 기록). 그만큼 크게 돌아 길어지고 안전해진다.
- 위치 추정: 엔코더가 없어 엉뚱한 곳에서 도착했다고 멈춘다. 길이는 오히려 짧아질 수 있어 길이로는 안 보인다.
- 도달 오차 0.447 m 는 0~2 단계에도 들어 있는 도착 판정 반경(0.45 m)이다. 우리 차에 맞게 줄일 것.

### 7단계. 현재. 남은 문제점

- **`walls`는 아직 예전 계획기보다 1.5초 느리다.** 벽 끝을 도는 곡선이 보수적이다.
- **`trap`에서 탐색이 가끔 1.2~1.6초까지 걸린다.** 매 계획마다 거리 추정을
  새로 만들고 탐색을 처음부터 한다. 지난 탐색을 재사용하는 방향이 다음 단계다.
- **공식 충돌 판정은 아직 뒷바퀴 축 기준이다.** 차체 기준 판정은 측정 스크립트에만 있다.
- **전체 시험이 수십 분 걸린다.** 예전 계획기 시험이 무겁다. 새 계획기 시험은 몇 초다.

이어서 고칠 사람을 위한 자세한 주의점은 `HANDOFF.md`에 있다.

## 현재 상태

충돌은 **차체 사각형 전체**와 실제 장애물 사이 거리로 쟀다. 두 계획기 모두 같은 조건이다.

| 시나리오 | 하이브리드 A\* 주행 | 차체 최소 여유 | 접선 그래프 주행 | 차체 최소 여유 |
|---|---|---|---|---|
| pillars | 18.5 s | 0.62 m | 25.0 s | 0.52 m |
| walls | 19.1 s | 0.44 m | 17.6 s | 0.65 m |
| narrow | 8.8 s | 0.30 m | 12.7 s | 0.70 m |
| trap | 20.9 s | 0.28 m | 34.2 s | 0.03 m |
| forest | 21.6 s | 0.29 m | 40.8 s | **-0.05 m, 접촉** |

`forest` 무작위 배치 여섯 개에서 하이브리드 A\*는 전부 도착, 차체 최소 여유 0.18 m 이상.

계획 한 주기(인식 포함) 평균은 하이브리드 A\*가 19~63 ms,
접선 그래프가 72~624 ms였다. 컴퓨터 부하에 따라 크게 달라진다.

`demo_pillars.mp4` 는 예전 접선 그래프 계획기의 주행 영상이다.
